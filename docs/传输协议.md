# 霜雪手机副机端 TCP / UDP 接入

本实现针对用户提供的 `霜雪AI瞄准手机副机端_7.18.apk.1.apk` 中的网络接收路径，保留原有 NDI。APK 未修改、未执行；兼容性依据为静态代码和本机协议测试，尚未完成 Windows → Android 实机验收。

## 使用

1. 手机选择“网络画面”，选择 TCP 或 UDP，启动接收，记下手机显示的 IP 和监听端口。代码中的默认端口均为 **7878**，以手机实际设置为准。
2. Windows FrameLink 中选择同一传输协议，目标填写 `手机IP:端口`（例如 `192.168.1.20:7878`）。默认 `127.0.0.1` 只用于本机测试，跨机器必须修改。
3. 设置采集区域、fps 和 JPEG 质量（1–100，默认 75），开始发送。TCP / UDP 无需 NDI DLL，不支持用 NDI 源名称发现手机。
4. UDP 若提示 JPEG 超过 65,507 字节，降低质量或尺寸，或改用 TCP。不能把图片任意拆成多个 UDP 包，否则该 APK 会把每一片当成一张图片解码。

TCP / UDP 由系统路由选择网卡，NDI 网卡限制不影响它们。支持字面 IPv4 和 `[IPv6]:端口`；不做 DNS 查询。手机与 Windows 防火墙和网络需允许对应端口。

## 协议

| 模式 | 实际发送字节 | 边界与限制 |
| --- | --- | --- |
| TCP | `[JPEG 1][JPEG 2]…` | 无长度头、无自定义帧头、无握手。APK 按 `FF D8` / `FF D9` 分离 JPEG，缓存上限 2 MiB |
| UDP | 一个数据报包含一整张 JPEG | 无自定义头、无应用层分片和重组；发送端最大 65,507 字节 |

图片为 baseline JPEG、YCbCr 4:2:0。图像宽高由 JPEG 本身携带；不发送音频、时间戳或帧号。不能用原始 NV12 / BGRX、RTP、H.264 或 FrameLink 自定义分片头替代 JPEG。JPEG 为有损编码，100 质量也不是数学无损。

UDP 大于链路 MTU 时仍可能产生 **IP 分片**，接收端系统只有收齐才能交付整个数据报。该 APK 没有应用层重传或纠错；因此 UDP 不保证完整接收率或比 TCP 更低延迟。协议没有接收确认、认证、加密或自动发现；按可信局域网使用。

## 性能设计

- 复用现有 DXGI / GDI 采集、双缓冲和固定帧率 / 跟随刷新率调度。
- TCP / UDP 路径采集紧凑 BGRA，释放 GPU Map 后再输入 JPEG 编码，不先转 NV12 再转回来。NDI 沿用原有 libyuv NV12 / BGRX 路径。
- 使用 `jpeg-encoder 0.7.1` 的 `simd` 功能，Windows x64 在运行时检测 AVX2，支持时使用 AVX2 编码路径，不支持时自动回退。不开启额外的优化 Huffman 或渐进编码。
- JPEG 输出缓冲复用；没有桌面更新时复用上次 JPEG，不重复编码。编码库内部仍有工作缓冲分配，不宣称零分配或零拷贝。
- 同一个工作线程采集、编码、提交，无应用层视频队列。TCP 直接写 JPEG 切片，UDP 直接一次提交 JPEG，不拼装分片或复制整张 JPEG 到包缓冲。
- TCP 启用 `TCP_NODELAY`，连接超时 500 ms，默认每张图写入预算 20 ms、以 5 ms socket 写超时检查停止和截止时间。超时停止并关闭连接，用户重新点击开始即可重连。预算可能超出一次系统调用和调度时间，不是硬实时上限。
- UDP 设置当前 socket 发送缓冲为 128 KiB，避免宿主默认缓冲小于一张 JPEG；不修改全局网络配置。非阻塞提交，本机暂不可写时丢弃这一帧，不堵塞等待；超大 JPEG 则明确报错停止，以免一直发送不可用数据。

JPEG 编码、无线网络、手机 JPEG 解码和模型推理都可能成为瓶颈，实际 fps 必须实测。帧率设置 240 不保证接收或推理也达到 240。传输带宽取决于画面复杂度与 JPEG 质量，不能再按原始 NV12 的固定带宽估算。

“实际发送”表示提交到本机 socket 的完整 JPEG 帧率，不代表手机已解码。UDP 接收设备显示未知，丢帧统计只包含本机因背压放弃的发送；网络/IP 分片丢失没有确认。TCP 的连接数 1 也不是解码确认。诊断 `conversion_ms` 包括 JPEG 编码；兼容旧 JSON 的 `ndi_submit_ms` 字段表示所选传输的提交耗时，`dropped` 记录本机 UDP 放弃数。二者均不代表端到端延迟。

## 静态分析依据

输入 APK SHA-256：`ca0160341066c6f8e856799932352b3cc12876f51c14b1230c29d82a359c6cfc`。

REA Android 接口缺少 `jadx-headless-mcp` JAR，实际 Java 检查使用官方 JADX **1.5.6** CLI，未执行 APK。以下是普通静态分析观察，不冒充 REA Evidence。Kotlin 协程部分无法恢复结构化 Java，改用 JADX `simple` 指令输出交叉确认。

| 位置（classes.dex） | 观察 |
| --- | --- |
| `m4.ia.i(Socket, long, fa)` | TCP 从 InputStream 读取，16 KiB 读块，累积上限 2,097,152 字节；调用 `j3.i.f(216, 0)` / `f(217, 2)` 搜索帧边界 |
| `j3.i.f(int, int)` | 逐字节匹配 `0xFF` 与传入标记；216 / 217 对应 JPEG SOI / EOI |
| `m4.k.d` 的网络帧分支 | 将识别出的 JPEG 区间交给 `m4.ia.f5080m` 帧通道 |
| `m4.ia.b(long, int, d5.c)` 的 simple 指令输出 | 创建 65,535 字节接收数组，`DatagramSocket.receive` 后按实际包长复制，单个包直接作为 `ea` 帧写入同一通道；这条路径没有应用层分片重组 |
| `c1.v.o(Object)` 的解码分支（simple 输出） | 取 `ea` 中的字节数组，调用 `BitmapFactory.decodeByteArray` |
| `m4.e7` 设置导入 / 导出；`m4.ia` 静态初始化 | UDP 和 TCP 默认端口 7878，可配置；网络帧率限制默认 240 |

只检查了网络视频接收边界及相关设置，没有改变 APK 的授权、模型、推理、控制回传或其他功能。其他 APK 版本是否使用相同协议未知。解码耗时、接收完整率和该设备实际处理能力仍需运行验证。

## 开发验证

参考接收器只匹配 APK 的 JPEG 边界并打印吞吐，不执行 Android 解码或模型推理：

```sh
cargo run --locked --release --example receive -- tcp 0.0.0.0:7878
cargo run --locked --release --example receive -- udp 0.0.0.0:7878
```

合成本机 JPEG 编码与 socket 基准，参数为协议、尺寸、fps、秒数（1–60）：

```sh
cargo run --locked --release --example transport_bench -- tcp 512 240 3
cargo run --locked --release --example transport_bench -- udp 512 240 3
```

使用变化的确定性纹理、JPEG 质量 75；包括每帧编码与发送，不包括屏幕采集、物理网卡、手机 JPEG 解码和推理。JSON 报告接收帧数、实际 fps、JPEG 带宽、编码+提交 p95 和错误。合成画面不能代表所有真实桌面复杂度。

测试覆盖连续 TCP JPEG 的任意拆包/粘包、短写、中断、背压截止时间、停止、UDP 一包一图、JPEG 独立解码与红蓝通道验证、超限 JPEG 在发送前拒绝、设置兼容。双机验收需额外检查：手机持续画面与颜色、实际接收/推理 fps、CPU、网络吞吐、断线与重连、UDP 超限提示、停止响应及完整控制回路延迟。

参考：[JPEG 编码库](https://github.com/vstroebel/jpeg-encoder)、[Rust TcpStream](https://doc.rust-lang.org/std/net/struct.TcpStream.html)、[Rust UdpSocket](https://doc.rust-lang.org/std/net/struct.UdpSocket.html)、[JADX](https://github.com/skylot/jadx)。

2026-11-02 的 Release 合成本机测试（macOS ARM64，JPEG 质量 75，每项 3 秒）：512 TCP / UDP 接收约 240.1 fps，640 TCP 约 240.1 fps、UDP 约 239.4 fps；这四次运行发送数与接收数一致。编码+提交 p95 分别约 2.47 / 2.66 / 2.69 / 2.91 ms。仅为本机短时可行性数据，不证明 Windows AVX2 路径、手机吞吐或长时间稳定性。[原始结果](validation/jpeg-loopback-2026-11-02.json)。
