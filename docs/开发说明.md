# 开发说明

FrameLink 使用根目录的 Cargo 工程，应用源码位于 `rust/`，可执行目标为 `FrameLink`。桌面应用面向 Windows x64，采集、转换和传输在后台工作线程中执行。

## 开发环境

- Rust 1.88+，Windows 构建使用 MSVC 工具链。
- Visual Studio 2022 C++ Build Tools 与 Windows SDK。
- Python 3，用于打包。

依赖版本由 `Cargo.lock` 固定。libyuv 源码位于 `third_party/libyuv/`，构建时静态链接。编译应用不需要 NDI SDK，NDI 运行库在运行时加载。

## 构建与打包

```powershell
cargo build --locked --release --target x86_64-pc-windows-msvc --bin FrameLink
```

输出为 `target/x86_64-pc-windows-msvc/release/FrameLink.exe`。

完整发布包需要官方 NDI Windows x64 运行库及其许可证。将以下三个文件放在同一目录：

```text
Processing.NDI.Lib.x64.dll
NDI License Agreement.pdf
Processing.NDI.Lib.Licenses.txt
```

运行打包命令：

```powershell
python tools/build_rust.py --target x86_64-pc-windows-msvc --ndi-runtime C:\NDI\Processing.NDI.Lib.x64.dll
```

输出为 `dist/FrameLink-版本号-Windows-x64.zip`，包含 EXE、NDI 运行库、文档和第三方许可。打包器检查 EXE / DLL 的 AMD64 PE32+ 格式、记录 SHA-256，并验证 ZIP 完整性。

| 参数 | 用途 |
| --- | --- |
| `--skip-build` | 打包已有的 Release 编译结果。 |
| `--output-dir` | 指定输出目录，默认 `dist/`。 |
| `--ndi-runtime` | 指定 NDI DLL，默认读取项目根目录。许可证需与 DLL 同目录。 |
| `--ndi-source-manifest` | 校验并保存运行库来源记录，文件摘要必须与实际输入一致。 |

MSVC 构建需要 Microsoft Visual C++ x64 运行库。应用的运行库加载方式和启动步骤见[使用说明](使用说明.md)。

### GNU 目标

也可使用 MinGW-w64 构建 Windows GNU 目标，需要完整的编译器及其自身依赖的 DLL，且 `x86_64-w64-mingw32-g++` 与 `x86_64-w64-mingw32-windres` 位于 PATH 中：

```sh
rustup target add x86_64-pc-windows-gnu
python tools/build_rust.py --target x86_64-pc-windows-gnu --ndi-runtime /path/to/Processing.NDI.Lib.x64.dll
```

GNU 版本静态链接 libstdc++。跨平台编译只生成 Windows 应用，运行检查仍需在 Windows 上进行。

## 运行机制

### 采集与发送

发送统一使用固定帧率，按 `max(previous + interval, now)` 计算下一次发送时间，过载时不追赶已经错过的时隙。DXGI 以零超时获取最新画面；没有新画面时复用已转换的像素，NDI 帧描述符使用配置中的 FPS。

DXGI 持有已获取的帧，直到下次 `AcquireNextFrame` 前释放。处理错误、恢复、退出和栈展开时也会释放所持帧，避免占用采集资源。自动模式可临时回退到 GDI，区域失效时停止并提示重新选择。

NDI 使用两份稳定的像素缓冲和描述符交替提交，退出时先等待发送端归还缓冲，再释放动态库。NV12 路径通过 libyuv 转换，BGRX 路径按实际行距复制。TCP / UDP 使用紧凑 BGRA 进行 JPEG 编码，具体行为见[传输协议](传输协议.md)。

可选 GPU NV12 路径位于 `rust/capture/gpu_nv12.rs` 与 `nv12.hlsl`。D3D11 先复制原尺寸区域到 GPU 纹理，再用计算着色器生成 NV12，回读后复制到原有稳定发送缓冲。内部行距按 4 字节对齐，提交 NDI 前去掉填充；颜色矩阵与 CPU 路径一致。该路径没有额外帧队列，也不是零拷贝。GPU 路径仅分配 NV12 回读缓冲，不创建 BGRA 读取纹理。

`gpu_nv12` 设置默认 `false`。不兼容的采集配置使用 CPU；GPU 初始化失败时记录回退原因，设备丢失仍走采集恢复流程。D3D11 功能级别至少为 11.0，着色器使用 Windows 的 D3DCompiler 47 在初始化时编译，不在发送循环中编译。

窗口可见时统计最多按 10 Hz 刷新，最小化或收到托盘后暂停持续重绘。界面只接收小型状态记录。

### 设置与单实例

设置在编辑后约 700 ms 保存，先写临时文件再替换正式文件。保存位置为 `%LOCALAPPDATA%\FrameLink\settings.toml`。

`fps` 接受 1–1000 的整数，默认 1000，`precision` 默认 `true`。加载旧版 TOML 或 INI 时忽略 `unlimited` 标记并保留 FPS；新保存的配置不再包含这个字段。

单实例锁按整台机器生效，与程序所在目录无关。重复启动通过事件唤醒已有窗口；恢复发生在原实例所在的交互桌面，前台激活受 Windows 焦点规则约束。进程退出后系统释放锁。`--ui-snapshot` 绕过单实例，不影响已有窗口。

### NDI 网卡配置

网卡选择保存 Windows AdapterName 标识，启动时通过 `GetAdaptersAddresses` 读取当前 IPv4。已断开或无地址的网卡不可新选；保存的网卡不存在时提示错误。

手动选择网卡时，应用读取原有 `NDI_CONFIG_DIR` 下的 `ndi-config.v1.json`，未指定目录时读取 `%ProgramData%\NDI`。只替换 `ndi.adapters.allowed`，保留其他字段，将结果写入 `%LOCALAPPDATA%\FrameLink\ndi\ndi-config.v1.json`。`NDI_CONFIG_DIR` 只在 FrameLink 进程内设置，不改写全局配置、系统网卡或路由。

切换网卡后需要“应用并重启”。重启先停止发送并释放单实例锁，再恢复原始配置环境启动新进程。发送前检查指定网卡是否在线、IP 是否变化。若检测到 `HKLM\SOFTWARE\NDI\Adapters` 下的 `Allowed` 管理配置，则提示使用自动模式。

## 测试

Windows MSVC 环境：

```powershell
cargo fmt --all -- --check
cargo test --locked --target x86_64-pc-windows-msvc --all-targets
cargo clippy --locked --target x86_64-pc-windows-msvc --all-targets -- -D warnings
cargo build --locked --release --target x86_64-pc-windows-msvc --bin FrameLink
python -m unittest discover -s tests -p "test_*.py"
```

Windows CI 执行以上检查。TCP / UDP 测试使用本机回环网络，需要运行环境允许 socket 通信。非 Windows 环境可用 `cargo test --locked --lib` 检查共享逻辑。

GPU 颜色测试需在有 D3D11 显卡的 Windows 桌面上单独运行，常规 CI 会跳过：

```powershell
cargo test --locked --release --target x86_64-pc-windows-msvc --lib hardware_gpu_nv12_matches_cpu -- --ignored --nocapture
```

测试覆盖三种色彩矩阵、裁剪偏移、非 4 字节对齐行宽、随机颜色、色条、灰阶，以及重复读取 NV12。

### 更新界面截图

```powershell
cargo run --locked --release --example ui_snapshot -- docs/ui
```

该命令离屏渲染实际界面控件，生成 NDI / TCP / UDP 两种窗口尺寸的截图，不采集桌面或修改用户设置。

### 单实例检查

先退出已有 FrameLink，在发布包解压目录运行：

```powershell
powershell -ExecutionPolicy Bypass -File tests/SingleInstanceVerification.ps1
```

在源码目录运行时，用 `-Executable` 指定被测 EXE。脚本检查重复启动、最小化和托盘恢复、并发启动及进程结束后的重启，只清理自身创建的进程。`close_to_tray = false` 时跳过关闭到托盘项。测试期间不要手动操作程序。

### 实机检查

- 多显示器、负坐标、不同 DPI、区域框选和设置保存。
- DXGI / GDI、不同固定帧率，以及 NDI 的两种像素格式。
- 三种协议的持续发送、接收画面与颜色、停止和断线恢复。
- 发送期间最小化、托盘恢复和重复启动。
- 分辨率变化、显示器拔插、锁屏和采集区域失效后的恢复。
- NDI 网卡切换、IP 变化和自动模式，确认系统配置保持完整。

测试记录应包含应用版本、机器配置、采集参数、协议和原始样本。跨机器测量需统一起止点并处理时钟差异；本机单元测试和像素基准不能替代完整传输测试。

## 诊断命令

在发布包解压目录运行：

```powershell
Start-Process .\FrameLink.exe -ArgumentList '--check-ndi' -RedirectStandardOutput ndi-check.json -Wait
Start-Process .\FrameLink.exe -ArgumentList '--benchmark-pixels','2' -RedirectStandardOutput pixels.json -Wait
Start-Process .\FrameLink.exe -ArgumentList '--measure-send','10','sender-report.json' -Wait
```

`--check-ndi` 验证程序目录内 NDI DLL 的加载、版本和初始化，不采集或发送画面。

`--benchmark-pixels` 运行 CPU 像素转换和复制基准，参数为每项持续秒数，不包含采集、编码或网络传输。

`--measure-send <seconds> <report.json>` 支持 1–60 秒。先在界面保存采集和传输参数并退出程序，再启动诊断；接收端保持运行。诊断沿用已保存设置，不写回配置，并遵守单实例规则。

可在本次诊断中覆盖帧率和 NDI 输入格式：

```powershell
Start-Process .\FrameLink.exe -ArgumentList '--measure-send','60','fps300.json','--fps','300','--pixel','nv12' -Wait
Start-Process .\FrameLink.exe -ArgumentList '--measure-send','60','fps500.json','--fps','500','--pixel','nv12' -Wait
```

`--fps` 接受 1–1000 的整数，`--pixel` 接受 `nv12` 或 `bgrx`。这些参数仅影响本次运行；省略 `--fps` 时沿用已保存的固定帧率。

使用 `--conversion cpu` / `--conversion gpu` 临时覆盖 NV12 转换方式。GPU 诊断要求 NDI NV12、DXGI 或自动采集，且不合成鼠标。每帧的 `gpu_conversion` 表示实际路径，`gpu_path_frames` 为该路径的帧数（包括重复帧），可据此识别回退。GPU 路径的 `map_wait_ms` 包含转换及回读等待，`conversion_ms` 只包含 NV12 到稳定内存的复制，不能单独用后者比较总耗时。

报告包含逐帧样本，以及帧释放、获取、GPU Map、转换或 JPEG 编码、传输提交的 p50 / p95 / p99 和最大值。等待桌面更新的时间单独统计，不计入“发送端处理”。

DXGI 帧龄由 `LastPresentTime` 与本机 QPC 计算，起点是整台显示器的最近桌面更新，即使变化发生在采集区域外也可能刷新。它不等于采集区域内容年龄或端到端延迟。GDI 不提供该时间戳。

NDI 样本的 `ndi_timecode_100ns` 与实际提交帧的时间码一致，可用于匹配接收记录；TCP / UDP 中该字段为 `null`。`capture_started_100ns` 记录开始调用采集的时间，不宜直接当作画面产生时间。

`source_present_100ns` 将 DXGI 桌面更新时间映射到 Unix UTC，`source_clock_uncertainty_100ns` 记录这次本机 QPC/UTC 配对的误差界限。字段单位均为 100 ns，单位不代表测量精度。两台机器的 UTC 仍需校准，步骤见[延迟测试](延迟测试.md)。

`tools/latency/analyze.py` 默认以桌面更新时间为起点，不需要测试绘制窗口。它按发送记录中的 `desktop_updated` / `refreshed` 事件关联重复帧，统计每次桌面更新的首次接收延迟；`primary_latency_ms` 是这个分布。没有新桌面更新时返回 `null`。可选 `--marker` 只用于分析包含绘制标记的记录。

`missing_diagnostic_samples` 表示有界诊断缓存缺失的样本及帧号区间，不表示网络丢帧。诊断会增加计时和记录开销，对照时应保持画面、负载、接收端和网络条件一致。
