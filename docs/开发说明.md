# 开发说明

FrameLink `3.1.2-dev` 使用根目录 Cargo 工程构建，应用代码位于 `rust/`，可执行目标为 `FrameLink`。支持 Windows x64 的采集、颜色转换及 NDI / TCP / UDP 发送。现有 AimRust 使用 NDI；TCP / UDP 采用所提供霜雪 7.18 APK 的 JPEG 接收协议，仍需手机实机验证。

## 模块

| 文件 | 职责 |
| --- | --- |
| `model.rs` / `settings.rs` | 参数验证、显示器坐标、设置保存和既有配置导入 |
| `capture.rs` / `capture/picker.rs` | DXGI / GDI、鼠标合成、DPI 坐标与桌面区域框选 |
| `capture_lease.rs` | DXGI 已获取帧的所有权、显式释放及退出清理 |
| `engine.rs` | 发送线程、启停、异常恢复、统计和预览邮箱 |
| `engine/send_pipeline.rs` | 统一发送分派、NDI 双缓冲和描述符生命周期 |
| `transport.rs` / `wire.rs` | TCP / UDP JPEG 发送、大小限制与参考 TCP JPEG 拆帧 |
| `examples/receive.rs` / `examples/transport_bench.rs` | 接收示例与合成 localhost 传输基准 |
| `ndi.rs` / `pixels.rs` | NDI ABI 与动态库、发送缓冲、libyuv SIMD 转换 |
| `policy.rs` | 帧率调度、双缓冲选择、恢复间隔与区域边界 |
| `ui.rs` / `tray.rs` | egui 窗口、托盘、参数编辑和状态反馈 |
| `single_instance.rs` | 进程互斥、重复启动通知和已有窗口恢复 |
| `network_adapters.rs` / `network.rs` | Windows 网卡枚举、进程 NDI 网卡配置和重启应用 |
| `snapshot.rs` / `examples/ui_snapshot.rs` | NDI / TCP / UDP 实际控件的离屏渲染，1200 / 960 两种尺寸 |
| `benchmark.rs` | 独立的 CPU 转换/复制基准，JSON 输出 |
| `diagnostics.rs` | Windows 发送采样、分位数统计及诊断报告 |
| `build.rs` / `resource_build.rs` | 编译 libyuv 和 Windows 图标、版本、manifest |

`third_party/libyuv/` 是当前 Rust 程序的颜色转换依赖，构建时静态链接，通过 FFI 调用。`resources/app.ico`、`rust.rc` 和 `rust.manifest` 用于 Windows 可执行文件。

仅选择 NDI 时，NDI DLL 在后台开始发送时加载。TCP / UDP 无需加载运行库；使用系统路由，不受 NDI 网卡配置约束。协议、性能边界与接收示例见[传输协议](传输协议.md)。缺失或加载失败时在界面显示错误；采集和 NDI 调用由工作线程处理。设置编辑后约 700 ms 保存，先写临时文件再替换正式文件。

单实例锁按整台机器生效，与可执行文件目录无关。重复启动通过事件唤醒原窗口；窗口只能在原实例所在的交互桌面恢复，前台激活受 Windows 焦点规则约束。进程退出后系统释放锁。开发参数 `--ui-snapshot` 绕过单实例，不影响已运行窗口。

## Windows 发送网卡

默认“自动选择”，保留用户现有 NDI 行为。指定网卡时，设置保存 Windows AdapterName 稳定标识，启动时通过 `GetAdaptersAddresses` 读取当前 IPv4；界面显示网卡名称、地址和协商发送速率，不把连接速率当作实测带宽。仅提供有 IPv4 地址的网卡，暂不提供 IPv6 单独绑定。已断开或无地址的网卡不可新选；保存的网卡不存在时提示错误，不自动切到其他网卡。

在 NDI 初始化前，将原有 `NDI_CONFIG_DIR` 下（未指定时为 `%ProgramData%\NDI`）的 `ndi-config.v1.json` 复制为内存配置，只替换 `ndi.adapters.allowed`，保留发现服务、分组和传输协议等其他字段。生成的文件位于 `%LOCALAPPDATA%\FrameLink\ndi\ndi-config.v1.json`，环境变量仅在 FrameLink 进程内设置；不写 Access Manager 的全局文件，不修改系统网卡、路由或注册表。自动模式不生成覆盖配置。

NDI 配置按进程启动生效，切换后通过“应用并重启”加载。重启先退出发送、关闭旧窗口并释放单实例锁，再启动新窗口；新进程恢复最初的 `NDI_CONFIG_DIR` 环境，避免“自动选择”误用上次生成的网卡限制。发送前检查指定网卡仍在线且 IP 未变化；变化后需要重启以重新读取。发送过程中拔线不会主动更换应用配置，需重新连接后停止并检查。

若检测到 `HKLM\SOFTWARE\NDI\Adapters` 的 `Allowed` 管理配置，手动选择会报错并提示使用自动模式，由系统 NDI 设置控制。配置文件格式错误或不可读也会明确提示。此功能使用标准 NDI SDK 的进程配置，兼容现有 NDI 接收软件；没有修改协议、编码器或接收端队列。`adapters.allowed` 控制主视频数据使用的适配器，不代表已验证所有发现流量和系统路由都绑定到该网卡。

## 采集与发送

- 固定帧率按 `max(previous + interval, now)` 计算下一截止时间，过载时不追赶历史时隙。
- 两份稳定像素缓冲和描述符交替使用，避免改写 NDI 正在使用的数据。退出时先等待 sender 归还缓冲，再释放资源与动态库。
- DXGI 持有当前获取的帧，直到下次 `AcquireNextFrame` 前才调用 `ReleaseFrame`，按[微软建议](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutputduplication-releaseframe)减少中间桌面更新引起的无用 GPU 复制。没有新增帧队列；资源处理错误、恢复、退出和 unwind 均释放所持帧，显式释放错误交给既有恢复流程。Windows 运行表现与收益仍待实机验证。
- NV12 无鼠标路径直接将 mapped BGRA 转换为 NV12；BGRX 按实际行距复制并去除填充。512 方形区域使用 BT.601，640 方形使用 BT.709，超过 1920 / 1080 使用 BT.2020。
- DXGI 暂时不可用时重试；自动模式固定帧率可暂用 GDI。区域超出有效桌面时停止并提示重选。
- 预览最多 2 fps、最大边长 320 像素，只保留一张最新预览。界面可见时统计最多按 10 Hz 刷新，最小化或收到托盘后暂停预览和持续重绘。

NDI 编码、网络、接收端背压和分析队列都可能增加帧龄。界面的平均调用耗时无法代表完整传输延迟，SDK 调用也可能阻塞停止过程。跟随刷新率模式在 `AcquireNextFrame` 里等待桌面更新，这段阻塞单独计入界面的“等新帧”，并从“发送端处理”中扣除；否则同一份处理耗时会随刷新率变化，两种模式无法比较。固定帧率的节拍等待发生在取帧之前，同样不计入处理耗时。

`--check-ndi` 仅验证应用目录内 Windows DLL 的加载与初始化，不采集或发流。构建时只链接 Windows libyuv 实现，已移除原生 Mac 采集、Swift / ScreenCaptureKit 依赖和 Mac 打包入口。

## 验证

本轮已通过 45 项共享逻辑单测、宿主库严格 Clippy、Windows GNU 全目标检查、严格 Clippy 和 Release 编译。Windows CI 提供 MSVC 全目标单测、严格 Clippy 和 Release 构建，但新增工作流是否通过应以实际运行结果为准。

采集、NDI 发送、托盘、单实例恢复、网卡绑定及双机延迟均需 Windows 实机验收。非 Windows 测试不调用 DXGI、Windows NDI DLL 或 GPU，也不能证明 240 fps 稳态。FrameLink 与 AimRust 联调应同时记录发送更新率、接收帧率、推理吞吐和帧龄，不能用单次模型推理时间代替整条链路。

1. 启动后检查显示器、512 / 640 预设、桌面框选、负坐标副屏和不同 DPI。重启后检查自定义区域与设置保存。
2. 固定 240 fps、DXGI，关闭鼠标与预览，分别使用 NV12 / BGRX 发送同一运动画面。记录接收 fps、CPU、网卡发送率及帧龄分布。
3. 切换预览、最小化、收起到托盘、双击托盘图标恢复、右键托盘菜单（停止发送 / 退出），检查画面连续性与资源释放。切换全屏、显示模式和锁屏，检查恢复或区域越界提示。
4. 发送期间再次启动程序，分别检查普通窗口、最小化和托盘状态：仅保留原 PID，恢复原窗口，源名称、区域与发送任务保持不变。
5. 对比延迟时统一测试画面、接收软件、负载和测量起止点。跨机器时间戳需校时；识别后点击回传测量的是完整控制回路。保留原始样本并检查波动，避免只比较平均值。
6. 同时接入有线和 Wi-Fi，在“发送网卡”选择有线并应用重启。确认选择保留、只有一个窗口、接收软件能重新发现源，并用任务管理器检查主视频流量所在网卡；对照自动模式时保持其他设置一致。再验证网卡改名、IP 变化、拔插、切回自动和已有外部 `NDI_CONFIG_DIR` 的情况，确认系统 NDI 配置未被改写。网卡绑定及延迟收益需 Windows 双机实测。

Windows 单实例自动验收（先退出已运行的 FrameLink）：

```powershell
powershell -ExecutionPolicy Bypass -File tests/SingleInstanceVerification.ps1 -Executable .\dist\FrameLink-3.1.2-dev-Windows-x64\FrameLink.exe
```

脚本随构建包放在 `tests/`，在解压目录运行时可省略 `-Executable`。它检查重复启动、最小化恢复、托盘恢复、并发启动及强制结束后重启，仅清理它创建的进程，不修改设置或自动开始发送。`close_to_tray = false` 时跳过关闭到托盘项。测试时请勿另外启动或操作程序。发送期间的连续性需按上述步骤人工验证。

Windows 发送诊断

先在 GUI 配好源名称、区域、帧率、格式和采集方式，等待设置保存后退出。保持接收软件运行，在解压目录运行以下命令，并确认接收端已重新连接同名源：

```powershell
Start-Process -FilePath .\FrameLink.exe -ArgumentList '--measure-send','10','sender-report.json' -Wait
```

`--measure-send <seconds> <report.json>` 支持 1–60 秒，沿用保存的采集设置，临时关闭预览且不写回配置。它遵守 Windows 单实例规则；已有 GUI 实例时先退出，避免命令只恢复原窗口。采样时播放持续运动画面，分别记录 512 / 640、NV12 / BGRX；对照时保持发送端负载、接收软件和网络一致。

报告包含逐帧原始样本，以及 `ReleaseFrame`、`AcquireNextFrame`、实际 `Map` 调用、转换、NDI 调用的 p50 / p95 / p99 / 最大值；DXGI 还记录 `AccumulatedFrames` 和 NDI 提交前后的桌面更新帧龄。帧龄使用 `LastPresentTime` 与 `QueryPerformanceCounter` 的同一计时基准计算，不依赖跨机校时。此帧龄来自整台显示器的最后桌面更新，即使变化发生在 ROI 外也可能刷新时间戳；它不是 ROI 内容年龄、网络耗时、完整 GPU 采集耗时或识别点击闭环延迟。GDI 不提供该 DXGI 时间戳。

NDI 异步调用也可能等待上一帧处理完成；调用耗时不能直接解释为网络延迟。原始样本和尾部分位数用于区分获取、GPU 读回和提交等待，先定位再调整。诊断本身会增加计时与记录开销，应把诊断运行和日常发送分开对照。

报告另列接收端连接观察和 `missing_diagnostic_samples`，用于检查测试是否连接接收端、统计是否缺样。诊断缓存有界，缺样会列出帧号区间；它不表示 NDI 网络丢帧。
