# 延迟测试

本页记录从发送端画面生成到接收端取得像素内存的测量。不包含接收端绘制、显示输出、AI 预处理、上传显存或推理。

## 计时范围

同一条链路使用三个起点：

| 指标 | 起点 | 终点 |
| --- | --- | --- |
| 画面生成到接收内存 | 测试程序开始绘制带时间标记的新画面 | NDI 返回完整解码像素缓冲 |
| 桌面更新到接收内存 | DXGI `LastPresentTime` | 同上 |
| NDI 提交到接收内存 | FrameLink 提交帧的 NDI 时间码 | 同上 |

第一项包含发送端绘制和桌面合成等待。后两项从链路中途开始计时，不能作为第一项的替代值。接收端在读取时间标记之前记录到达时间，不为测量绘制画面。

## 2026-11-04 对照结果

- 发送端：Windows x64、Radeon RX 9070 XT，DXGI 采集 640 × 640 区域，鼠标和预览关闭。
- 接收端：Intel N100、Linux x64，NDI 6.3.2 完整带宽接收，两端有线链路协商速率为 2.5 Gbps。
- 画面：带 UTC 时间标记和反码校验的动态色块，生成速率约 144 帧/秒。
- 每种配置测量两轮，每轮预热 3 秒、记录 30 秒，共 48,955 帧有效接收记录；逐帧匹配与时间标记校验均通过。
- 每轮前后校准两端 UTC，校时不确定度上界约 0.35 ms。数据基于 `e5d56c6` 与诊断插桩，直接缓冲另用实验原型。

以下均为**画面生成到接收内存**，单位为 ms，接收输出统一为 BGRX：

| 发送配置 | 中位数 | P95 | 不同画面到达率 |
| --- | ---: | ---: | ---: |
| 固定 240 fps，NV12 | 11.47 | 12.35 | 96.0 帧/秒 |
| 跟随刷新率，NV12 | 9.29 | 9.91 | 144.0 帧/秒 |
| 跟随刷新率，BGRX | 9.39 | 9.99 | 144.0 帧/秒 |
| 跟随刷新率，直接映射 BGRX 缓冲原型 | 9.32 | 10.00 | 143.8 帧/秒 |

固定帧率接收约 240 帧/秒，其中含重复画面；表中的到达率按不同时间标记计数。跟随刷新率 + NV12 的总延迟中位数降低约 19%，桌面更新到接收内存的中位数约 2.95 ms。

直接缓冲原型交替使用两张 staging 纹理，将映射后的指针交给 NDI，并保持映射直到异步发送归还所有权。它省去了约 0.06 ms 的应用内 BGRX 复制，但没有显示出优于现有 NV12 路径的总延迟；正式发送路径继续使用稳定双缓冲。该原型仍包含 GPU 读回、编码和解码，不能称为整条链路零拷贝。

另测“跟随刷新率 + NV12，接收原生 UYVY”，中位数为 8.98 ms，P95 为 9.64 ms。此结果尚未进行 YUV 到 RGB 转换，应结合接收端实际预处理评估。

完整统计见 [JSON 记录](validation/ndi-latency-2026-11-04.json)。这些数值仅描述本次画面与设备；首次到达统计也不表示源程序绘制的每一帧都被接收。小于校时误差的差异不作为确定的性能提升。

## 复测

`tools/latency/` 提供以下源码，不附带 NDI 二进制或设备连接信息：

| 文件 | 用途 |
| --- | --- |
| `Marker.cs` | 生成带 UTC 时间标记的窗口，按时自动退出。 |
| `receive.py` | 接收完整 NDI 帧，记录返回像素内存的时间及可选的画面标记。 |
| `calibrate.py` | 从发送机经 SSH 校准 Linux 接收机的 UTC 偏移。 |
| `analyze.py` | 逐帧匹配发送记录、校正时钟并区分新画面与重复帧。 |

需要当前源码构建的 FrameLink、Python 3，以及各平台官方 NDI 运行库。接收和离线分析仅使用 Python 标准库；SSH 校时额外需要 `paramiko`，接收机需有 `python3`。校时不修改系统时间，不启动常驻服务。

### 1. 准备发送端

在界面保存 DXGI、NDI 和 640 × 640 采集区域，退出 FrameLink。记下实际区域左上角坐标，并确保接收机可以连接 NDI 源。

在仓库根目录编译标记窗口：

```powershell
New-Item -ItemType Directory -Force tests/results/ndi | Out-Null
& "$env:WINDIR\Microsoft.NET\Framework64\v4.0.30319\csc.exe" /nologo /target:winexe /r:System.Drawing.dll /r:System.Windows.Forms.dll '/out:tests\results\ndi\Marker.exe' '.\tools\latency\Marker.cs'
```

先用正常 SSH 连接确认接收机的主机密钥，再在**发送机**校时。以下地址和用户名需替换为实际值：

```powershell
python -m pip install paramiko
python tools/latency/calibrate.py --host RECEIVER_HOST --user SSH_USER --output tests/results/ndi/clock-before.json
```

默认使用 SSH 密钥或 agent。需要密码时加 `--password`，程序会无回显询问，不接受命令行密码。

### 2. 启动画面、发送与接收

下面以区域左上角 `(960, 480)` 为例。标记窗口的位置和大小必须与采集区域一致；`$senderExe` 指向当前源码构建的程序，NDI DLL 应在其旁边。

```powershell
$senderExe = '.\target\x86_64-pc-windows-msvc\release\FrameLink.exe'
Start-Process .\tests\results\ndi\Marker.exe -ArgumentList '960','480','640','55','tests/results/ndi/render.json'
Start-Process $senderExe -ArgumentList '--measure-send','60','tests/results/ndi/sender.json','--follow-refresh','--pixel','nv12'
```

在 Linux 接收机准备好命令，在发送启动后立即运行。需要将 `receive.py` 放在接收机，并指定其本地 NDI 运行库路径：

```sh
python3 receive.py --runtime /path/to/libndi.so.6 --source 'SENDER (FrameLink)' --seconds 30 --warmup 3 --color bgrx --marker --output receiver.json
```

源发现不可用时可补充 `--url SENDER_IP:PORT`，端口以实际源为准。`--color fastest` 请求 SDK 原生格式，报告中的 FourCC 表示实际返回格式。

标记窗口持续 55 秒，发送持续 60 秒，接收记录必须落在标记窗口运行期间。比较固定帧率时将 `--follow-refresh` 换成 `--fps 240`；比较 BGRX 输入时使用 `--pixel bgrx`。每轮使用新的输出文件名。

### 3. 校时与分析

接收完成后在发送机再次运行 `calibrate.py`，输出为 `clock-after.json`。等待发送诊断结束，将接收机的 `receiver.json` 和 `receiver.csv` 取回 `tests/results/ndi/`，然后执行：

```powershell
python tools/latency/analyze.py --sender tests/results/ndi/sender.json --receiver tests/results/ndi/receiver.json --clock-before tests/results/ndi/clock-before.json --clock-after tests/results/ndi/clock-after.json --output tests/results/ndi/result.json
```

分析输出包含汇总 JSON 和匹配后的 CSV。发送机与接收机是同一操作系统实例时，可用 `--same-clock` 替代两份校时文件；不能因为两台机器均启用了自动校时就使用该选项。

原始接收报告中的时间差尚未校正，不能直接作为跨机延迟。分析假设两次校时之间没有时钟跳变；出现负延迟、时间标记失效、发送样本缺失或格式变化时，应排查后重测。首次出现的画面标记可能已在预热阶段到达，因此不计入新画面首次到达统计。
