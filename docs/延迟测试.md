# 延迟测试

## GPU NV12 转换对照

2026-11-04，固定 300 fps，在 RX 9070 XT 发送端和 N100 接收端上对比 CPU / GPU 转换。每个尺寸按 CPU、GPU、GPU、CPU 顺序运行；每轮预热 3 秒、接收测量 15 秒，共收到 36,008 帧，接收速率约 300 fps。采集和发送尺寸相同，不使用测试绘制窗口。

下表为中位数，单位 ms。“采集→提交”从调用采集开始，到向 NDI 提交为止，不含固定帧率等待和 NDI 后续编码；“桌面→接收内存”从 DXGI 桌面更新时间开始，到接收端获得解码后的 BGRX 内存为止，包括固定帧率等待。

| 尺寸 | 转换 | 采集→提交 | 桌面→接收内存 |
| --- | --- | ---: | ---: |
| 416 × 416 | CPU | 0.192 | 3.938 |
| 416 × 416 | GPU | 0.171 | 3.893 |
| 640 × 640 | CPU | 0.293 | 4.693 |
| 640 × 640 | GPU | 0.183 | 4.479 |

GPU 路径在这台发送端减少了约 0.02 ms / 0.11 ms 的处理时间。但跨机校时不确定度最大为 ±0.356 ms，416 的接收端耗时也存在轮次波动，尚不能据此确认完整链路稳定改善。接收端绘制、应用复制、GPU 上传和 AI 不在测量范围内；本次也未覆盖游戏占满显卡的情况。

24 组硬件像素校验中，GPU 与 CPU 输出逐字节一致。GPU 转换保持原尺寸，回读数据量从每像素 4 字节降到 1.5 字节，之后仍会复制到稳定的 NDI 缓冲。该功能默认关闭，可在高级设置中启用。完整百分位、逐轮接收速率及方法见[数据记录](validation/ndi-gpu-nv12-2026-11-04.json)。

默认测量从桌面画面可被采集开始，到接收端取得完整像素内存为止。保留实际屏幕采集，不启动测试绘制窗口；不计入源程序绘制、之前的桌面合成等待、接收端绘制、显示输出、AI 预处理、上传显存或推理。

## 计时范围

默认报告使用以下两个起点：

| 指标 | 起点 | 终点 |
| --- | --- | --- |
| **桌面更新到接收内存（主要指标）** | DXGI `LastPresentTime` | NDI 返回完整解码像素缓冲 |
| NDI 提交到接收内存 | FrameLink 提交帧的 NDI 时间码 | 同上 |

第一项包含采集、转换、NDI 编码、网络传输与接收解码。第二项不包含 NDI 提交前的采集和转换，不能代替第一项。接收端在 SDK 返回完整像素缓冲时立即记录到达时间。

## 2026-11-04 固定帧率实测

Windows DXGI 采集当前桌面 640 × 640 区域，NV12 发送到 Intel N100 Linux 接收机，返回 BGRX 像素。两端有线链路为 2.5 Gbps，开启精确定时、关闭预览和鼠标，不启动测试绘制窗口。

| 固定帧率 | 中位数 | P95 | 接收进程占 N100 总 CPU |
| --- | ---: | ---: | ---: |
| 300 fps | 4.39 ms | 6.00 ms | 14.6% |
| 500 fps，同批对照 | 3.03 ms | 3.97 ms | 15.3% |
| 1000 fps，前批两轮 | 2.29 ms | 2.74 ms | 23.3% |

300 fps 测了两轮各 30 秒，中间穿插一轮 500 fps；1000 fps 来自此前两轮各 30 秒。每轮预热 3 秒并在前后校时，表中校时不确定度不超过约 0.33 ms。原始构建为 `97bdca9`，使用其固定帧率路径；后续移除了跟随模式。

当前桌面每秒约有 38–43 次更新，其余发送帧为重复画面。表中延迟按每次桌面更新首次到达计算，不代表每一帧都是新画面，也不包含 AI。300 fps 的发送端 CPU 用时比同批 500 fps 约低 49%，但 NAS 接收端 CPU 差距较小。

这些数字适用于本次分辨率、画面和设备，不是帧率对应的固定延迟。更高 FPS 需要更多处理资源；接收端应持续取帧，推理只处理最新画面。统计记录见 [固定帧率对照](validation/ndi-fixed-fps-2026-11-04.json)。

## 历史计时对照

以下使用旧版“跟随刷新率 + NV12 → BGRX”的两轮记录，按桌面更新时间重新分析 8,640 个更新。当前版本已移除跟随模式，历史数据仅供对照：

| 阶段 | 中位数 | P95 |
| --- | ---: | ---: |
| 桌面更新 → NDI 提交 | 0.32 ms | 0.39 ms |
| NDI 提交 → 接收内存 | 2.63 ms | 2.93 ms |
| **桌面更新 → 接收内存** | **2.95 ms** | **3.27 ms** |

这是同一批数据改用明确的计时起点，不是新增的性能提升。原始条件和数据如下；新的默认复测流程不需要绘制窗口。

## 2026-11-04 历史对照：包含画面生成

- 发送端：Windows x64、Radeon RX 9070 XT，DXGI 采集 640 × 640 区域，鼠标和预览关闭。
- 接收端：Intel N100、Linux x64，NDI 6.3.2 完整带宽接收，两端有线链路协商速率为 2.5 Gbps。
- 画面：带 UTC 时间标记和反码校验的动态色块，生成速率约 144 帧/秒。
- 每种配置测量两轮，每轮预热 3 秒、记录 30 秒，共 48,955 帧有效接收记录；逐帧匹配与时间标记校验均通过。
- 每轮前后校准两端 UTC，校时不确定度上界约 0.35 ms。数据基于 `e5d56c6` 与诊断插桩，直接缓冲另用实验原型。

以下均为**画面生成到接收内存**，单位为 ms，接收输出统一为 BGRX：

| 发送配置 | 中位数 | P95 | 不同画面到达率 |
| --- | ---: | ---: | ---: |
| 固定 240 fps，NV12 | 11.47 | 12.35 | 96.0 帧/秒 |
| 跟随刷新率，NV12 | 9.29 | 9.91 | 144.0 帧/秒 |
| 跟随刷新率，BGRX | 9.39 | 9.99 | 144.0 帧/秒 |
| 跟随刷新率，直接映射 BGRX 缓冲原型 | 9.32 | 10.00 | 143.8 帧/秒 |

固定帧率接收约 240 帧/秒，其中含重复画面；表中的到达率按不同时间标记计数。跟随刷新率 + NV12 的总延迟中位数降低约 19%，桌面更新到接收内存的中位数约 2.95 ms。

直接缓冲原型交替使用两张 staging 纹理，将映射后的指针交给 NDI，并保持映射直到异步发送归还所有权。它省去了约 0.06 ms 的应用内 BGRX 复制，但没有显示出优于现有 NV12 路径的总延迟；正式发送路径继续使用稳定双缓冲。该原型仍包含 GPU 读回、编码和解码，不能称为整条链路零拷贝。

另测“跟随刷新率 + NV12，接收原生 UYVY”，中位数为 8.98 ms，P95 为 9.64 ms。此结果尚未进行 YUV 到 RGB 转换，应结合接收端实际预处理评估。

完整统计见 [JSON 记录](validation/ndi-latency-2026-11-04.json)。这些数值仅描述本次画面与设备；首次到达统计也不表示源程序绘制的每一帧都被接收。小于校时误差的差异不作为确定的性能提升。

## 无绘制窗口复测

`tools/latency/` 提供以下源码，不附带 NDI 二进制或设备连接信息：

| 文件 | 用途 |
| --- | --- |
| `receive.py` | 接收完整 NDI 帧，记录返回像素内存的时间。 |
| `calibrate.py` | 从发送机经 SSH 校准 Linux 接收机的 UTC 偏移。 |
| `analyze.py` | 匹配 NDI 时间码、校正时钟，并按发送端桌面更新记录区分更新与重复帧。 |

需要当前源码构建的 FrameLink、Python 3，以及各平台官方 NDI 运行库。接收和离线分析仅使用 Python 标准库；SSH 校时额外需要 `paramiko`，接收机需有 `python3`。校时不修改系统时间，不启动常驻服务。

### 1. 准备发送端

在界面保存 DXGI、NDI 和实际需要的采集区域，退出 FrameLink。正常运行要采集的应用，并确保接收机可以连接 NDI 源。发送诊断自动关闭预览，不保存这些临时设置，也不开启 FrameLink 界面。

先用正常 SSH 连接确认接收机的主机密钥，再在**发送机**校时。以下地址和用户名需替换为实际值：

```powershell
python -m pip install paramiko
python tools/latency/calibrate.py --host RECEIVER_HOST --user SSH_USER --output tests/results/ndi/clock-before.json
```

默认使用 SSH 密钥或 agent。需要密码时加 `--password`，程序会无回显询问，不接受命令行密码。

### 2. 启动发送与接收

`$senderExe` 指向当前源码构建的程序，NDI DLL 应在其旁边。只启动发送诊断：

```powershell
$senderExe = '.\target\x86_64-pc-windows-msvc\release\FrameLink.exe'
Start-Process $senderExe -ArgumentList '--measure-send','60','tests/results/ndi/sender.json','--fps','300','--pixel','nv12'
```

在 Linux 接收机准备好命令，在发送启动后立即运行。需要将 `receive.py` 放在接收机，并指定其本地 NDI 运行库路径：

```sh
python3 receive.py --runtime /path/to/libndi.so.6 --source 'SENDER (FrameLink)' --seconds 30 --warmup 3 --color bgrx --output receiver.json
```

源发现不可用时可补充 `--url SENDER_IP:PORT`，端口以实际源为准。`--color fastest` 请求 SDK 原生格式，报告中的 FourCC 表示实际返回格式。

发送持续 60 秒，接收记录必须落在发送运行期间。比较固定帧率时修改 `--fps` 后的数值，例如 300、500 或 1000；比较 BGRX 输入时使用 `--pixel bgrx`。每轮使用新的输出文件名。

### 3. 校时与分析

接收完成后在发送机再次运行 `calibrate.py`，输出为 `clock-after.json`。等待发送诊断结束，将接收机的 `receiver.json` 和 `receiver.csv` 取回 `tests/results/ndi/`，然后执行：

```powershell
python tools/latency/analyze.py --sender tests/results/ndi/sender.json --receiver tests/results/ndi/receiver.json --clock-before tests/results/ndi/clock-before.json --clock-after tests/results/ndi/clock-after.json --output tests/results/ndi/result.json
```

分析输出包含汇总 JSON 和匹配后的 CSV。主要看 `primary_latency_ms`，它统计每次桌面更新的首次接收延迟。默认报告不包含绘制计时。发送机与接收机是同一操作系统实例时，可用 `--same-clock` 替代两份校时文件；不能因为两台机器均启用了自动校时就使用该选项。

初始桌面更新可能已在预热阶段到达，因此不计入首次到达统计。后续重复帧放在 `all_arrivals_including_repeats_ms` 中；静止桌面没有有效的新更新时，`primary_latency_ms` 为 `null`，不会把旧画面的年龄冒充新帧延迟。

DXGI 时间戳对应整台显示器，采集区域外的变化也可能触发更新。这个指标不能证明裁剪区域内容发生变化，也不代表每次桌面更新均成功送达。GDI 没有对应时间戳，不能据此报告桌面更新延迟。

原始接收报告中的时间差尚未校正，不能直接作为跨机延迟。分析假设两次校时之间没有时钟跳变；出现负延迟、发送样本缺失或格式变化时，应排查后重测。

### 历史绘制记录

`Marker.cs` 仅保留用于复现历史画面生成测试，默认流程不编译或运行它。分析带画面标记的旧记录时，可给 `analyze.py` 加 `--marker`，额外输出 `render_start_to_decoded_ms`；新接收记录只有显式加 `receive.py --marker` 才会读取画面标记。
